PROBLEM STATEMENT & MOTIVATION

Problem Statement & Industry Motivation

Critical security failures in modern repository workflows, open-source supply chains, and legacy scanning tools

01 / Secret Leakage in Git

  • Accidental Commits: Developers push API tokens, database passwords, and private keys into git repositories.
  • Persistent History: Deleting a token in a later commit does not purge it from git history; attackers easily extract raw objects from commit graphs.
  • Cloud Compromise: Exposed credentials lead to immediate cloud infrastructure takeovers and data breaches.

02 / Supply Chain Risks (SCA)

  • Heavy Dependency Ratio: Over 85% to 90% of modern software consists of third-party open-source libraries.
  • Transitive Vulnerabilities: Deep dependency trees mask critical known CVEs (e.g. Log4Shell, prototype pollution) without developer awareness.
  • Unmonitored Upgrades: Automated package upgrades frequently introduce compromised upstream packages.

03 / Fatigue & Blindness

  • Alert Fatigue: Legacy static analysis tools dump hundreds of unranked warnings lacking business context.
  • Missing Remediations: Scanners state that a flaw exists, but fail to provide contextual, copy-paste code patches.
  • Runtime Gap: Static tools inspect code strictly at rest, leaving running servers blind to live HTTP attacks.
Slide 2 Talking Points:
Here is the core problem statement: First, credentials leak into git history, where attackers easily harvest them. Finally, fragmented tooling leaves security teams without centralized audit trails, and static tools remain blind to active HTTP attacks.

SYSTEM ARCHITECTURE & REQUEST FLOW

System Architecture: End-to-End Request Pipeline

Single-origin FastAPI and React SPA request flow, isolated route boundaries, and sandboxed execution

Architectural Tier Decomposition

• Tier 1 / Presentation Layer (React 18 + Vite): Independent routing shells for /admin/ and /user/. Strict separation of UI routes from JSON APIs eliminates boundary collision.

• Tier 2 / API Gateway & Middleware (FastAPI): FastAPI serves both JSON APIs and compiled React SPA assets on a single origin, completely eliminating CORS attack surfaces. Enforces HttpOnly session cookie guards and rate limits.

• Tier 3 / Asynchronous Engine Pipeline: Background runner clones target repositories into ephemeral sandboxes (/tmp/veritas-scans), executes multi-engine scans, and persists findings via SQLAlchemy.

Pipeline Execution Workflow

• Step 01 / Inbound Trigger Validation: Scans are triggered manually or via GitHub push webhooks. Webhooks verify X-Hub-Signature-256 HMAC signatures using the project secret.

• Step 02 / Ephemeral Sandbox Workspace: Repository is cloned into a short-lived directory under VERITAS_SCAN_ROOT. Branch references and changed-file diff lists are extracted.

• Step 03 / Multi-Engine Normalization: 12 CLI scanners execute in parallel/sequence. Outputs are mapped into standardized finding schemas with SHA-256 fingerprints.

• Step 04 / Dual AI Reasoning & SARIF: OpenRouter reviews logic; Groq Llama-3 writes executive risk reports and patches. Sandbox is wiped and SARIF 2.1.0 is saved.

Slide 4 Talking Points:
Let's look at the software architecture. VERITAS employs a unified single-origin model: FastAPI serves both the backend APIs and the compiled React frontend. Hosting the SPA on the same origin completely eliminates CORS exposure and allows secure HttpOnly session cookies to work natively without cross-domain leakage.

SECURITY PILLAR 4: CI/CD AUTOMATION

Render-Style GitHub Push CI/CD & Sandboxing

Automated continuous repository scanning without developer friction, token leakage, or lingering files

Continuous Push CI/CD Sequence

• Step 01 / Git Push Event: Developer pushes commits to the watched branch on GitHub. No CLI tool execution or manual intervention required.

• Step 02 / Webhook HMAC SHA-256 Validation: GitHub delivers push payload to /webhooks/github. VERITAS verifies X-Hub-Signature-256 using the per-project secret.

• Step 03 / Ephemeral Sandbox Workspace: Repository is cloned into an isolated temporary workdir under /tmp/veritas-scans. Scans track the 7-character short commit SHA.

• Step 04 / Multi-Engine Scan & Purge: Engines and AI pipelines evaluate the checkout. Immediately upon completion, the sandbox workdir is wiped from disk.

Operational CI/CD Safeguards

• Server-Side Repo Ownership Check: User links GitHub via OAuth. VERITAS queries GitHub API on every attach to strictly verify that the connected user owns the repo, blocking forged ID injection.

• Encrypted OAuth Tokens at Rest: GitHub access tokens are encrypted using Fernet (AES-128-CBC + HMAC-SHA256). Tokens are never returned to client browsers.

• Sub-Minute PR Diff Scans: Using scan_scope: changed, Semgrep is restricted to files changed in git diff against default branch, delivering rapid feedback for pull requests.

• Compute Quota Enforcement: SCAN_RATE_LIMIT (10/hr) and SCAN_CONCURRENT_LIMIT (2) prevent host exhaustion during rapid multi-commit pushes.

Slide 8 Talking Points:
To make security seamless for developers, Phase 5 introduced Render-style auto-scan on push. A developer links their GitHub account, selects their repository, and turns on auto-scan. VERITAS registers a repository webhook verified with HMAC SHA-256 signatures. Every push to the watched branch triggers an automated scan.

DEFENSIVE ENGINEERING

Defensive Engineering: Platform Security Posture

Practicing what we preach: robust architectural hardening and fail-closed safeguards across the platform

Security Domain Implementation & Mechanism Threat Mitigated & Defensive Value
Session Hardening veritas_session cookie with HttpOnly, SameSite=Lax, and Secure flags. SHA-256 hashed DB tokens. Mitigates XSS session theft and eliminates exposure of valid sessions if database backups are compromised.
Account Recovery Password resets immediately invalidate and delete all active session rows across all user devices. Eliminates lingering sessions if an account was compromised prior to password reset.
Authorization Guardrails Fail-closed role checks. Blocks deactivating the last active admin; admins cannot alter own role. Mitigates privilege escalation attacks and prevents accidental platform lockout.
Host Protection /admin/files restricts traversal; blocks /proc, /sys, /dev, /etc/shadow, and .env files. Prevents Local File Inclusion (LFI) and accidental disclosure of server credentials.
Slide 12 Talking Points:
As a cybersecurity platform, VERITAS must be thoroughly hardened itself. We followed defense-in-depth principles: all cookies use HttpOnly and SameSite flags; all tokens in the database are hashed; and our authorization model is strictly fail-closed. We prevent privilege escalation by disallowing admins from changing their own roles, and ensure the system always has at least one active administrator.
